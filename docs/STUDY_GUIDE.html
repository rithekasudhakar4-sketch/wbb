Nalam Nagar Emergency Dispatch & Route Optimization

Complete Student Study Material, Code Walkthrough, and Viva Defense Guide (Pure Java, Zero Frameworks)

1. The Big Picture

1.1 The Operational Problem in Nalam Nagar

Imagine a growing town named Nalam Nagar with 12 residential, industrial, and commercial zones. In traditional manual emergency response centers, dispatchers face four critical flaws:

  • Triage Inversion (First-Come Trap): If a patient calls with a mild sprained ankle at 10:00 AM and another patient suffers a cardiac arrest at 10:01 AM, a simple FIFO queue sends the available ambulance to the ankle sprain. The cardiac patient dies waiting.
  • Distance vs. Time Fallacy: Assigning an ambulance because it is geographically 2 km away often results in long delays if that road is congested or blocked by construction, while a 4 km highway bypass could be 10 minutes faster.
  • Hospital Specialty & Bed Mismatch: Patients are rushed to the nearest clinic, only to discover at the door that it lacks an ICU or has zero available beds, requiring a dangerous second transfer.
  • Fleet Repositioning Blindness: After dropping off a patient at a hospital, an ambulance is now stationed at that hospital zone. Manual centers forget this and dispatch units from distant stations.

1.2 Real-Life Scenario: Ravi's Emergency

Let's follow a single emergency from start to finish:

  1. The Accident: At 10:15 AM, Ravi Sharma suffers severe industrial burn injuries at Residential Colony A (Zone L3).
  2. Call Intake: The operator enters the details: Patient: Ravi Sharma, Location: L3, Condition: BURN, Severity: CRITICAL, Unit: BURN_UNIT.
  3. Triage Enqueue: The system assigns CRITICAL (priority 0). Even with 5 minor flu calls already waiting, Ravi jumps immediately to Rank #1.
  4. Hospital Selection: The system scans all 5 hospitals. Only Sanjeevani Burn & Critical Care (H4) at College Road (L5) has a dedicated Burn Unit. The system verifies H4 has 2 free beds and calculates the fastest path from L3 to L5 (4.0 km, 9.0 min), reserving a bed instantly.
  5. Ambulance Selection: The system checks available ambulances:
    • AMB-1 at Central Hospital: 12.0 min away
    • AMB-2 at Bus Terminal: 15.0 min away
    • AMB-5 at Market Circle: 7.0 min away (Winner!)
  6. Look-Ahead Total Mission Time: $7.0\text{ min (Amb } \to \text{ Pt)} + 9.0\text{ min (Pt } \to \text{ Hosp)} = \mathbf{16.0\text{ minutes}}$.
  7. Delivery & Repositioning: AMB-5 delivers Ravi to Sanjeevani Hospital (H4). Once admitted, AMB-5 is freed and stationed at College Road (L5), ready for the next call in that district.

2. Concepts Explained Simply

Concept 1: Graph Network & RoadGraph

Real-Life Analogy: Think of a town road map as a connect-the-dots drawing. The dots (neighborhoods, crossroads) are Nodes. The lines (roads, avenues) are Edges.

Plain Explanation: A graph stores connections between points. In Nalam Nagar, roads are bidirectional and store two weights: physical distance in km and travel time in minutes. Our system strictly optimizes for travel time in minutes.

Small Example with Numbers: Node L1 (Central Hospital) connects to Node L6 (Bus Terminal) with Distance = 2.5 km and Travel Time = 6.0 minutes.

Where it appears in MY code: src/graph/RoadGraph.java using private final Map<Location, List<Road>> adjacencyList;.

⚠️ Common Mistake
Using a 2D Matrix (double[][]) for a sparse graph. With 12 nodes and only 16 roads, an Adjacency Matrix wastes space on empty cells ($O(V^2)$). An Adjacency List only stores roads that actually exist ($O(V + E)$).

Concept 2: Dijkstra's Algorithm & RoutePlanner

Real-Life Analogy: Water spreading through irrigation trenches. It fills the closest trench first, then ripples outward into the next closest branch.

Plain Explanation: Dijkstra's Algorithm guarantees the shortest path from a starting node to all other nodes on graphs with non-negative edge weights ($w \ge 0$). It maintains a Distance Table and a Min-Heap Priority Queue to explore the node with the smallest accumulated travel time next.

Step-by-Step Distance Table Progression (From L1 to L8):

Step Extracted Node Time Inspected Neighbor Edge Time Calculated Time Previous Best Table Action
Init - - - - L1 = 0.0 $\infty$ Set L1 = 0.0
1 L1 0.0 L9, L6, L3, L11 5.0, 6.0, 12.0, 9.0 0 + 5.0 = 5.0 ... $\infty$ Update L9, L6, L3, L11
2 L9 5.0 L4 10.0 5.0 + 10.0 = 15.0 $\infty$ Update L4 = 15.0
3 L6 6.0 L2, L7 8.0, 11.0 6.0 + 8.0 = 14.0 $\infty$ Update L2 = 14.0
4 L2 14.0 L8 15.0 14.0 + 15.0 = 29.0 $\infty$ Update L8 = 29.0
5 L8 29.0 Destination Reached! - - - Terminates!

Optimal Path Reconstructed: L1 -> L6 -> L2 -> L8 with Total Travel Time = 29.0 minutes (12.0 km).

Time Complexity: $O((V + E) \log V)$. For Nalam Nagar ($V=12, E=32$), it takes $\approx 157$ operations, executing in under 0.1 milliseconds!

💡 Viva Tip
Why do we have if (timeU > minTime.get(u)) continue; in RoutePlanner.java? Because Java's PriorityQueue lacks an $O(\log V)$ decreaseKey(). We add new entries when edge relaxations improve distances, and discard stale duplicate entries when they are polled.

Concept 3: PriorityQueue Triage

Real-Life Analogy: An Emergency Room triage nurse. A cardiac arrest patient arriving at 10:05 AM is treated immediately ahead of a mild flu patient who arrived at 10:00 AM.

Plain Explanation: A `PriorityQueue` serves elements based on priority instead of FIFO arrival. In Java, it is backed by a Binary Min-Heap.

Why it beats sorting a List: Inserting into a `PriorityQueue` is $O(\log N)$ and peeking the top is $O(1)$. Re-sorting an `ArrayList` on every call takes $O(N \log N)$, causing severe lags during mass-casualty events.

Where it appears in MY code: src/model/EmergencyRequest.java:

@Override
public int compareTo(EmergencyRequest other) {
    // 1. Primary order: CRITICAL (0) < SERIOUS (1) < MINOR (2)
    int severityComparison = Integer.compare(this.severity.ordinal(), other.severity.ordinal());
    if (severityComparison != 0) {
        return severityComparison;
    }
    // 2. Secondary order (FIFO for tie-breaking): earlier timestamp comes first
    return Long.compare(this.timestamp, other.timestamp);
}

Concept 4: Two-Leg Dispatch Logic

Real-Life Analogy: Calling an Uber to take you to the airport. The system must find the driver closest to you (Leg 1), and then calculate the route from you to the airport (Leg 2).

Plain Explanation: Emergency dispatch combines two legs: $$\text{Leg 1 (Response): } \text{Ambulance} \to \text{Patient} \quad (\text{lowest response time})$$ $$\text{Leg 2 (Transport): } \text{Patient} \to \text{Hospital} \quad (\text{appropriate medical unit and free beds})$$ $$\text{Total Mission Time} = \text{ETA}(\text{Leg 1}) + \text{ETA}(\text{Leg 2})$$

Where it appears in MY code: DispatchManager.java (lines 130–165) and AutoDispatcher.java (lines 143–223).

Concept 5: REST API and JSON

Real-Life Analogy: A restaurant waiter carrying standard order slips between diner tables (the browser) and the kitchen chef (the Java backend).

Plain Explanation: REST uses standard HTTP verbs (GET to fetch data, POST to submit data). JSON is human-readable text formatting data into key-value pairs (e.g. {"patientName": "Ravi", "severity": "CRITICAL"}).

Concept 6: Embedded HTTP Server (`WebServer`)

Real-Life Analogy: A mobile coffee cart with its own built-in generator and espresso machine that operates without renting an entire commercial building.

Plain Explanation: Instead of heavy enterprise servers like Tomcat or Spring Boot, we use Java's built-in com.sun.net.httpserver.HttpServer on port 8080. It starts in under 1 second with zero external dependencies.

Where it appears in MY code: src/WebServer.java.

Concept 7: Concurrency, Thread Safety & Preemption

Real-Life Analogy: Two dispatchers sharing a single physical clipboard. Whoever holds the clipboard has exclusive access to assign ambulances, preventing both from assigning the same vehicle.

Plain Explanation: The web server handles HTTP requests on worker threads while AutoDispatcher runs on a background daemon. To prevent race conditions, both synchronize on dispatchLock.

What is Preemption? If an ambulance is en route to a Minor call and an urgent Critical cardiac call arrives with no free fleet units, the system re-routes the ambulance to the Critical patient and puts the Minor call back into the queue.

Where it appears in MY code: src/service/AutoDispatcher.java (lines 125 and 260–301).

Concept 8: Frontend Polling

Real-Life Analogy: Checking the oven every 2 minutes while baking cookies to see if they are ready.

Plain Explanation: In frontend/app.js, setInterval(pollCurrentPage, 2000) queries /api/status, /api/queue, and /api/ambulances every 2 seconds to update the screen live without a page refresh.

Concept 9: Relational Database & Transactions

Real-Life Analogy: An ATM cash withdrawal. If cash fails to dispense, the bank must rollback the deduction from your balance. Either both happen, or neither does.

Plain Explanation: In AutoDispatcher.persistDispatchTransaction(), we execute: 

conn.setAutoCommit(false); // Begin transaction
try {
    ambulanceDao.updateStatus(conn, ...);
    hospitalDao.updateAvailableBeds(conn, ...);
    emergencyDao.updateStatus(conn, ...);
    conn.commit();   // Commit all 3 together
} catch (SQLException ex) {
    conn.rollback(); // Rollback if any fails!
}

5. Design Decisions & Trade-Offs

PriorityQueue vs. ArrayList Sort

Chosen: Min-Heap PriorityQueue.

Reason: $O(\log N)$ enqueue vs $O(N \log N)$ full list sorting on every arrival.

Dijkstra vs. A* Search

Chosen: Dijkstra's Algorithm.

Reason: Straight-line Euclidean distance heuristic can overestimate winding road times with dynamic closures, violating A* admissibility. Dijkstra runs in < 0.1 ms.

Adjacency List vs. Matrix

Chosen: Map<Location, List<Road>>.

Reason: Sparse graph (12 nodes, 16 roads). Avoids wasting memory on zero-cells.

In-Memory Graph + SQLite

Chosen: In-memory routing, SQLite persistence.

Reason: Recursive SQL graph queries are slow. In-memory Dijkstra gives nanosecond responses, while SQLite ensures ACID durability.

Group 1: Basic & Foundational Questions

Q1: What is the main objective of your project?
It is an automated emergency ambulance dispatch and route optimization system for Nalam Nagar that eliminates manual triage delays, finds the fastest travel routes using Dijkstra's algorithm, matches patients to hospitals with specialized beds, and automatically coordinates fleet movements.
Q2: Why do you optimize by travel time instead of geographic distance?
Geographic distance does not account for traffic bottlenecks, road closures, or speed limits. A road that is 2 km long might take 15 minutes due to heavy traffic, while a 4 km bypass might take only 6 minutes. In medical emergencies, saving minutes saves lives.
Q3: How many town zones, ambulances, and hospitals are in the system?
There are 12 simulated zones (L1 to L12), 5 strategically stationed emergency ambulances (AMB-1 to AMB-5), and 5 specialized hospitals (H1 to H5).
Q4: What data structure did you use to store the road network?
An Adjacency List graph (Map<Location, List<Road>> in RoadGraph.java). Each vertex maps to a list of outgoing directed Road objects.
Q5: What are the edge weights in your graph?
The primary edge weight used by Dijkstra is travelTime in minutes. Each edge also stores physical distance in kilometers and an isClosed boolean flag.
Q6: How does the system handle road closures?
In RoadGraph.java, roads have a boolean flag isClosed. The method getActiveRoads() filters out any edge where isClosed == true. Dijkstra only evaluates active roads, automatically skipping blocked paths.
Q7: What algorithm is used for route planning, and what is its time complexity?
Dijkstra's Shortest Path Algorithm using a binary min-heap (PriorityQueue). Its time complexity is $O((V + E) \log V)$, where $V$ is vertices (zones) and $E$ is edges (roads).
Q8: What data structure handles triage in the emergency queue?
Java's java.util.PriorityQueue<EmergencyRequest>, which is implemented internally as a binary min-heap.
Q9: How are emergency requests prioritized in the queue?
By implementing Comparable<EmergencyRequest>. The primary sorting key is the Severity enum ordinal (CRITICAL = 0, SERIOUS = 1, MINOR = 2). Ties are broken using FIFO arrival timestamp (Long.compare(this.timestamp, other.timestamp)).
Q10: What are the three severity levels in your system?
CRITICAL (immediate life-threat, e.g., cardiac arrest, extensive burns), SERIOUS (urgent medical intervention, e.g., respiratory distress, pediatric crises), and MINOR (non-life-threatening illness or fractures).

Group 2: Intermediate Technical Questions

Q16: Explain how Dijkstra's algorithm reconstructs the final path in your code.
During edge relaxation, whenever a shorter time to neighbor $v$ via $u$ is found, we store $u$ in previous.put(v, u). Once the destination is reached, we backtrack from destination to source following the previous map, store the nodes in a list, and reverse it (Collections.reverse(path)).
Q17: Why does your Dijkstra implementation check `if (timeU > minTime.get(u)) continue;`?
Because Java's PriorityQueue does not support an $O(\log V)$ decreaseKey operation. When a shorter path is found, we re-insert the node with the smaller time. When the older, larger duplicate is polled, this check recognizes it as stale and skips it.
Q18: What is Look-Ahead Total Mission Time?
It is the combined two-leg duration: the time for the fastest ambulance to reach the patient (Leg 1) plus the time to transport the patient to the chosen hospital (Leg 2).
Q22: How does the system ensure thread safety between HTTP handlers and AutoDispatcher?
Both WebServer.java HTTP handlers and AutoDispatcher.java synchronize on a shared monitor object: dispatchLock. Any state-altering method runs inside synchronized (dispatchLock) { ... }, preventing race conditions.
Q23: What is preemption and how does AutoDispatcher implement it?
Preemption reassigns a resource from a low-priority task to an incoming high-priority task. If a CRITICAL emergency arrives and all ambulances are busy, findPreemptableAmbulance() re-routes an ambulance currently en route to a MINOR call, returning the minor call to the queue.
Q26: Explain the database transaction in `AutoDispatcher.persistDispatchTransaction()`.
It sets conn.setAutoCommit(false), updates the ambulance to busy, decrements hospital beds, and sets the emergency to DISPATCHED. If all three succeed, conn.commit() is called. If an exception occurs, conn.rollback() reverts all three.

Group 3: Tricky & Design Choice Questions

Q31: Why didn't you use A* search instead of Dijkstra?
A* requires an admissible heuristic like straight-line Euclidean distance. In urban routing with dynamic road closures and traffic delays, Euclidean distance can overestimate true travel times, making A* inadmissible. Given our town scale of 12 zones, Dijkstra runs in under 0.1 ms, making A* heuristics an unnecessary complication.
Q32: Why store the road network in memory if you already have a relational database?
Relational databases are optimized for tabular CRUD operations, not recursive pointer-hopping graph traversals. Running Dijkstra inside SQL queries is slow and complex. Storing the graph in-memory provides sub-millisecond pathfinding, while the database ensures durable audit logging.
Q35: Can Dijkstra's algorithm handle negative road weights? Does your code handle them?
No, Dijkstra fails on negative edge weights because it assumes once a node is settled, its shortest distance cannot decrease. However, road travel times are physical durations which are always strictly positive ($t > 0$). In RoadGraph.java, updateTravelTime() explicitly validates if (newTravelTime <= 0) return false;.
Q37: What prevents two ambulances from being assigned to the same patient?
In AutoDispatcher.runDispatchCycle(), requests are immediately removed from the queue with dispatchManager.pollNextRequest(), and the selected ambulance status is set to EN_ROUTE_PATIENT inside a synchronized (dispatchLock) block.

9. Technical Glossary

Term One-Sentence Definition
Adjacency List A graph data structure where each vertex stores a list of its connected neighbor edges.
Binary Heap A complete binary tree that satisfies the heap property, where the root is always the minimum or maximum element.
PriorityQueue A queue collection where elements are dequeued based on priority level rather than arrival order.
Dijkstra's Algorithm A greedy algorithm that finds the guaranteed shortest path from a source node to all other nodes with non-negative edge weights.
Edge Relaxation The process of testing whether passing through an intermediate vertex improves the known shortest distance to a neighbor.
Look-Ahead ETA The total projected mission duration combining ambulance-to-patient response time and patient-to-hospital transport time.
Preemption The interruption of an active low-priority task to reallocate its resource to an urgent high-priority arrival.
REST An architectural style for networked web services communicating via HTTP verbs like GET and POST.
JSON A lightweight, text-based data interchange format based on key-value pairs.
Daemon Thread A background Java thread that does not prevent the JVM from exiting when all user threads finish.
Race Condition A concurrency flaw where program correctness depends on the unpredictable execution order of multiple threads.
PreparedStatement A pre-compiled SQL statement used to execute parameterized queries safely, preventing SQL injection.
ACID Transaction A database transaction satisfying Atomicity, Consistency, Isolation, and Durability guarantees.
Polling A technique where a client regularly queries a server at fixed time intervals to fetch state updates.
Triage The medical protocol of sorting patients into priority categories based on clinical urgency.
